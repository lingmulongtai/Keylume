# v0.5.1 検証記録

2026-09-25。エフェクト使用中の無音と、出力先変更で復帰しない経路を対象にした修正版です。

## 再現した原因

`instrument_fx.rs`のコーラス用循環バッファで、`f32::rem_euclid`の丸めにより読み出し位置がバッファ長と同じ値になりました。長さ1920、書き込み位置818、遅延818の次の表現可能なfloatを与えると、位置が1920となり配列の範囲外参照でpanicします。旧実装では、この境界テストとノブ変更を伴う長時間処理テストの両方が失敗しました。

Windows音声コールバックはLooperのmutexを保持してエフェクトを処理するため、panicが音声スレッドを終了させ、共有ロックもpoisonします。使用中のCPAL 0.15.3 WASAPI実装はこのpanicをエラーコールバックへ通知せず、ストリーム破棄時のthread joinもpanicし得ます。そのため出力先の切り替えだけでは復帰できない構造でした。

整数化した読み出しインデックスにも循環処理を追加しました。さらにDSP処理の内側で異常を捕捉し、最大64フレーム単位で元の音を復元、エフェクトの履歴・位相・平滑化値を初期化します。正常経路にロックやヒープ割当を追加せず、音声スレッド、演奏中のノート、Looperを保持します。非有限の元信号は0へ置換します。

コーラス用の読み出しはコーラス量0でも動いていました。今回の再現は無音・復帰不能の故障経路を示すもので、物理ノブ操作だけが唯一の発生条件とは断定しません。

## 回帰テスト

- バッファ終端への丸めと、終端をまたぐ補間値。
- 22.05 / 44.1 / 48 / 96kHzで各120秒分、8パラメーターを繰り返し変更する連続処理。出力が有限かに加え、異常からの復旧処理を一度も使っていないことを確認。
- Looperロック保持中にエフェクトのpanicを注入。元の左右音声、録音イベントと録音モードが維持され、mutexがpoisonされず、その後のwet処理が成功することを確認。
- NaN / Infinityを内部状態と入力へ注入。有限の出力を復元し、後続1000ブロックが正常処理されることを確認。
- 従来のdry信号維持、残響、全パラメーター最大値のテスト。

## Windows音声出力

普段使いのアプリと設定領域・identifierを分け、Mock MIDI入力とWindowsの実音声コールバックで検証しました。物理Launchkeyからの入力や、スピーカーからの実際の聴取・遅延測定とは区別します。

- 48kHz、コールバック480フレーム。同梱UprightとGeneralUser GSの`generaluser:0:3`が非ゼロの出力ピークを生成。
- GeneralUser GSでライブノートと3イベントのループを鳴らし、181.7秒間に8ノブへ合計4,000回のCC入力。最初にCCが実際にエフェクト設定へ反映されることを確認。
- 約10秒ごとに18回、発音とループの時計の進行を確認。最後に保存されたピーク値を見ているだけではないことを検査し、録音イベント数も維持。
- 出力先の固定指定と「Windowsの既定」の切り替えを実行。同じ実出力デバイス上でストリームを再作成し、全音停止でピーク0になった後、新しいノートで再び非ゼロになることを確認。
- 出力再作成後も録音を保持し、消去とUndoで3イベントを復元。音声スレッドのpanicログなし。
